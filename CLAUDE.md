# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # Start dev server
npm run build        # Production build
npm run typecheck    # TypeScript check (no emit)
npm test             # Run every test suite
npm test <filtro>    # Only suites whose path matches, e.g. `npm test pagos`
npm run shipping-v2:schema  # Regenerate Airtable schema for shipping-v2
```

## Tests

There is no Jest/Vitest. Tests are standalone `assert()` scripts (~178 of them,
under `**/__tests__/*.test.ts`) executed with `tsx`. **Always run them through
`npm test`** (`scripts/run-tests.mjs`), never with a bare `npx tsx`, because the
runner knows three things that are easy to get wrong:

1. **`NODE_OPTIONS="--conditions react-server"` is mandatory** for any suite that
   reaches `lib/shipping-v2/airtable.ts` or any other `import "server-only"`
   module. Without it the suite dies on the first import and *looks* broken when
   it is merely mis-invoked — that is exactly what happened to six suites.
2. **A few suites need the opposite** (they pull in client components through
   `lib/permissions/pantallas.ts` → `next/navigation`). The runner retries those
   without the flag automatically.
3. **Seven facturación suites talk to the real Airtable/SRI** and stop
   themselves with exit code 78 (see `lib/facturacion/__tests__/_guardaRed.ts`).
   The runner reports them as *omitidas*, not failures. To run them on purpose:
   `PRUEBAS_CON_RED=1 npm test <filtro>` — and read the guard's comment first,
   there is no test base in Airtable.

Green baseline: **171 pass, 7 omitidas, 0 failures.** Anything else is a
regression. Habit worth keeping: every money or inventory fix starts by pulling
the pure logic into its own module with a test that reproduces the bug first.

## Environment Variables

Required in `.env.local`:

| Variable | Purpose |
|---|---|
| `SESSION_SECRET` | JWT signing secret |
| `AIRTABLE_API_KEY` | Airtable PAT — used by every module (portal users, técnicos, operaciones, shipping-v2, facturación) |
| `AIRTABLE_BASE_ID` | The single Airtable base ("SUPER GEEK ADM") shared by every module |
| `AIRTABLE_USERS_TABLE` | Users table name in the base |
| `RESEND_API_KEY` | Email sending via Resend |
| `BLOB_READ_WRITE_TOKEN` | Vercel Blob storage |
| `AIRTABLE_ACCESS_LOG_TABLE` | Access log table (optional) |
| `CRON_SECRET` | Bearer token Vercel Cron sends to `/api/cron/*` routes (e.g. `operaciones-depurar-cotizaciones`, see `vercel.json`); the route rejects any request without a matching `Authorization: Bearer` header |

Shipping V2 reads its env vars at runtime; running `npm run shipping-v2:schema` uses `.env.local` to fetch the live Airtable schema and regenerates `lib/shipping-v2/schema.generated.ts`.

## Architecture

### Tech Stack
- **Next.js App Router** (v16) with React 19 — all pages under `app/`
- **Airtable** as the sole database — no SQL, no ORM, raw REST API calls
- **JWT sessions** via `jose` — stored in HTTP-only cookies (`sg_staff_session`)
- **Tailwind CSS** + shadcn/ui primitives in `components/ui/`

### Authentication Flow
1. `proxy.ts` (exported as the Next.js middleware via `middleware.ts`) handles all route protection
2. Login → bcrypt password check → optional 2FA (10-minute pending cookie) → full session cookie (8 hours)
3. Session payload carries `userId`, `rol`, and `appsPermitidas` (array of permitted app names)
4. `lib/session.ts` — JWT create/verify; `lib/auth.ts` — password hashing/checking

### Permission Model
`lib/apps.ts` is the single source of truth for the permission model:
- `staffApps[]` — registry of all apps with their `permissionName` and `requiredRoles`
- `canAccessApp(session, appName)` — normalizes Unicode, case-insensitive match against `appsPermitidas`
- Administrators (`rol === "admin" | "administrador"`) bypass all per-app checks
- Each API module has its own `requireXSession()` guard (e.g. `lib/tecnicos/api-auth.ts`, `lib/shipping-v2/auth.ts`)
- `lib/permissions/pantallas.ts` adds a second, finer layer **within** a module: per-user, per-screen visibility (deny-list, module → hidden screen keys), stored as JSON in the `Usuarios."Pantallas Restringidas"` field and baked into the session JWT (`SessionUser.pantallasRestringidas`) same as `appsPermitidas` — a change applies on next login, not instantly. Piloted on Shipping V2 (`requirePantallaVisible()` guards every `app/shipping-v2/**/page.tsx`); configured by an Administrator from `/admin/usuarios`.
- `lib/permissions/campos.ts` is Phase 2, built on top of Phase 1: per-user, per-field state (`"oculto"` | `"solo-lectura"`, absence = editable) within a screen that has a field catalog — today only Shipping V2's Item detail screen (`SHIPPING_V2_ITEM_EDIT_FIELDS` in `lib/shipping-v2/item-edit-config.ts`). Stored as JSON in `Usuarios."Campos Restringidos"`, same JWT/next-login semantics as pantallas. `Cantidad` (and any other `adminOnly` field) is deliberately excluded from this configurable catalog — it keeps its own absolute, non-overridable admin-only lock instead. Enforced server-side in `updateShippingV2ItemField`/`updateShippingV2Item` (write) and via `ocultarCamposDeObjeto()` at the API-route/page boundary (read) — never inside `getShippingV2ItemById()` itself, since internal callers (despiece, packing lookups) need the real values regardless of who's viewing a screen.

### Single Airtable Base
Every module reads/writes the **same Airtable base** ("SUPER GEEK ADM"), via `AIRTABLE_API_KEY` + `AIRTABLE_BASE_ID`: portal users, access logs, 2FA codes, `Órdenes de Reparación`, `Clientes`, `Operación Comercial`, `Abonos`, `Shipping Items`, `Facturas Electrónicas`, etc. (see `lib/shipping-v2/schema.generated.ts` for the shipping-v2 tables). Técnicos previously read/wrote a separate base via `AIRTABLE_TECNICOS_TOKEN`/`AIRTABLE_TECNICOS_BASE_ID` — that migration is complete and those variables are no longer used anywhere in the codebase; don't reintroduce them.

This means data from different modules (e.g. an order's linked client, or a Shipping Item referenced from an invoice) can be fetched with the same credentials, without cross-base joins.

**`docs/ESQUEMA.md` is the map of the base**: the table inventory, how to query the live schema, and — importantly — which Airtable computed fields the code deliberately ignores (`Total Cubierto`, `Saldo Item`, `Total Cotizado`, `Saldo Pendiente`). Read it before trusting any calculated field you see in an Airtable view. There is no full-schema JSON snapshot in `docs/` and none should be added; only `lib/shipping-v2/schema.generated.ts` is versioned, and it is regenerated by script.

### Module Structure Pattern
Each feature module follows this layout:
```
app/[module]/              # Pages (Server Components by default)
app/api/[module]/          # Route handlers
lib/[module]/              # Server-side logic, Airtable calls
  api-auth.ts              # requireXSession() guard for API routes
  airtable.ts or airtable/ # Airtable fetch helpers
components/[module]/       # Client components for this module
types/[module] or types/[module].ts  # Shared TypeScript types
```

### Layout Shell
`StaffAppShell` (async Server Component in `components/staff/StaffAppShell.tsx`) is the standard wrapper for all authenticated pages. It fetches the session and visible apps, then renders `StaffAppFrame`. Pages import it directly — there's no layout.tsx per-module.

### Middleware
The middleware logic lives in `proxy.ts` (root) and is re-exported from `middleware.ts`. The `config.matcher` in `proxy.ts` controls which paths are intercepted.

### Shipping V2 Schema
`lib/shipping-v2/schema.generated.ts` is auto-generated — do not edit by hand. Run `npm run shipping-v2:schema` after any Airtable schema changes. The script (`scripts/inspect-shipping-v2-schema.mjs`) calls the Airtable Metadata API using `.env.local`.

### Estado de cuenta (saldo del cliente)
There is ONE calculator for a customer account (an order plus all its operations, or a standalone operation): `lib/estado-cuenta/reglas.ts` (`calcularEstadoCuenta`, `resolverEstadoPago`, `pendientesDeLaCuenta`). Two readers feed it the same data: `getCuentaUnificada()` (one account, detailed) and `lib/estado-cuenta/airtable.ts` (many accounts, in bulk — Cobros panel, Operaciones board). Never compute a total, saldo or payment status anywhere else, and never read Airtable's "Total a Pagar NV" / "Saldo NV" / "Total Abonado NV" for it (legacy, to be removed). `lib/estado-cuenta/__tests__/loteIgualDetalle.test.ts` guards that both readers agree.
Discounts are per line in the Airtable table "Descuentos de Cuenta" (admin only, never deleted, only "Anulado"); rules in `lib/estado-cuenta/descuentos.ts`, writes only through `lib/estado-cuenta/descuentos-servidor.ts`. A discount is never a negative service; on invoices it is the line's `descuento` (`aplicarDescuentoALinea` in `lib/facturacion/gancho/construccion.ts`).

### Métodos de cobro (dinero que entra)
ONE catalog: `lib/cobros/metodos.ts` (method → Finanzas account, state, Finanzas "Método", SRI code, requires transaction number). Abonos, mostrador invoices/receipts, reservations, venta adicional and the Finanzas bridges all use it. Screens never offer SRI codes: the employee picks the method; servers derive the SRI code (`normalizarCobrosNuevos`) and reject a new payment without a valid method. The only account-less income allowed is SRI "15" (credit-note compensation, no new money), paying with the client's saldo a favor (same idea) and a parte de pago (see below).

Parte de pago (2-nov-2026): the client hands over an item (a used disk, a laptop) as part of the payment. "Parte de pago" in CuentaUnificadaPanel → `lib/parte-pago/servidor.ts` (`recibirParteDePago`): creates a Shipping item (tipo "Parte de pago de cliente", cost = agreed value, already in store, always "por revisar"; Kardex motivo "Parte de pago del cliente") + an abono with método "Parte de pago" (never offered in "Registrar pago") + an account-less Ingreso "Parte de pago de cliente". SRI: compensación de deudas (15). Anyone who collects can register it; only an admin can annul it (abono DELETE → `prepararAnulacionParteDePago`), and only while the item is still free in store (it is then dado de baja). Pure rules in `lib/parte-pago/reglas.ts`.

Money that LEAVES to pay suppliers (purchases, freight, duties) also has ONE catalog: `lib/shipping-v2/cuentas-pago.ts` ("Cuenta origen" value → Finanzas account; e.g. "Tarjeta C. Produbanco" → PRODUBANCO MASTERCARD, "Transferencia SGINGRESOS" → SGINGRESOS). Every payment screen offers `CUENTAS_PAGO_VIGENTES`; the server validates against it and the egreso resolves its account from it.

Each payment (abono > 0) of an account has a non-tax 'Comprobante de abono' (ticket 80 mm + PDF A4, Facturación style): pure rules in lib/cobros/comprobante-abono.ts, read in comprobante-abono-servidor.ts, PDF via lib/documentos/pdf-base.ts (shared base for new A4 PDFs). Links live in CuentaUnificadaPanel.

### Saldo a favor del cliente (dinero de más)
ONE balance per client: Airtable table "Saldo a Favor" (movements: Generado +, Usado/Devuelto/Vencido/Ajuste −; each Generado expires in 6 months, consumed earliest-expiring first). Pure rules in `lib/saldo-favor/reglas.ts`; all writes through `lib/saldo-favor/servidor.ts` (routes `.../saldo-favor` for orders and operations). An account with money left over never keeps it: "Pasar a saldo a favor" writes a NEGATIVE abono (método "Saldo a favor") + a Generado + an account-less Egreso "Saldo a favor de cliente"; "Devolver" (admin only) writes a negative abono (método "Devolución") + an Egreso from a real account. Paying with the balance is a positive abono "Saldo a favor" + Usado + account-less Ingreso; on invoices it is SRI "15", and negative abonos are netted out of the payment lines (`calcularFormasPago`). The abono bridge never books these abonos. Released reservations generate balance automatically. Credit notes with destino "Cambio de equipo"/"Saldo a favor" and released reservations generate balance automatically; a credit note's "Saldo Disponible" is only a MIRROR of its lot (`sincronizarNotasCredito`). Mostrador invoices/receipts can pay with "Saldo a favor" (SRI 15): the server checks the balance before emitting (`verificarSaldoParaDocumento`) and books the Usado after (`consumirSaldoEnDocumento`, idempotent per document). Since point 22 (6-nov-2026, case OR000525) the VENTA ADICIONAL of an invoice/receipt emitted from an order/operation can also be paid with "Saldo a favor": same check in `validarEmisionDesdeOrigen`, Usado booked after emission (only the venta adicional lines; the account abonos are ignored), account-less Ingreso in `crearMovimientosVentaAdicional`, and voiding the receipt gives the balance back. The abono forms warn when the amount exceeds what is owed (`lib/cobros/aviso-abono.ts`): what the client buys on the way out is charged as venta adicional, not as an abono. Expiry runs daily in `/api/cron/saldo-favor-vencido` (`vencerSaldos`); the old NC caducidad skips NCs already in the ledger. The client file (`/tecnicos/clientes/[id]`) shows the balance on top and the client's whole history in one list (`lib/clientes/historial.ts` pure, `historial-servidor.ts` reads; route `.../clientes/[id]/historial`); an admin can return an existing balance from there (`devolverSaldoDeCliente`: Devuelto + account-less Ingreso "Saldo a favor de cliente" + Egreso "Devolución" from the real account).

### Compras para clientes (solicitudes de compra)
Auditoría ops, Fase 2 (puntos 9, 3, 8, 12). What a customer approved and the shop must buy is a row in the Airtable table "Solicitudes de Compra" (SOL-000001; states Por comprar → Comprada → Entregada / Cancelada; "Llegó"/"Entregado" are read from the item, never stored). It is born automatically, once per key (`linea:recX` / `opcion:recX`): a "bajo pedido" budget line approved by the client (`asegurarSolicitudDeLinea`, from `lib/tecnicos/presupuesto/cargar.ts` — NO Operación Comercial is created anymore) or an approved option of a customer order (`asegurarSolicitudDeOpcion`, from `/api/operaciones/[id]/estado`). Buying is always done by Staff/Admin (never técnicos) in the ONE purchase screen, "Registrar compra" (`/shipping-v2/items/nuevo?solicitudes=…`), opened from the inbox `/shipping-v2/compras`; the items POST takes `solicitudId` and `aplicarCompra` reserves the new item for its order (via `cargarCompraEnLinea`, the line becomes "Cargada" — cargar.ts stays the only file that loads charges onto an order) or for its operación (links + reserved units, op → "Pedido"). "Ya la tenemos" (`asignarArticuloExistente`) reserves an existing item. "Pedido" in Operaciones and the old "Ya se pidió al proveedor" no longer create items (Fase 2B removed that second door: `pasarOperacionAPedido`, `crearShippingItemDesdeOpcion`, `createShippingV2ItemFromOperacion`, `marcarPedidoAlProveedor`, `crearOperacionAprobada`). Old orders whose bajo-pedido lines still point to an Operación Comercial keep working through that operation. Receiving an item (Recepción "Recibido") calls `alRecibirArticulo` → internal notification only (no customer messages). Pure rules (anticipo coverage = full client price, chip per line, validations, "¿Es para OR…?" matching) in `lib/compras/reglas.ts`; server in `lib/compras/servidor.ts`.

### Productos digitales (point 5A, 7-nov-2026)
Each unit has an SKU `DIG-000001` (Airtable autoNumber "N° Digital" + formula "SKU") and lookups "Orden (ID)", "Cliente (Nombre)", "Factura (Número)", "Recibo (Número)". Credentials depend on the catalog TYPE (`lib/productos-digitales/reglas.ts`, `camposDeCredenciales`/`credencialesDelTipo`): "Clave de activación" → key only; "Usuario/Contraseña"/"Suscripción" → user + password only; "Otro" → both. The create route drops what does not belong and the credentials/PDF readers filter by type, so a stray key never reaches the client's PDF. Never use `<input type="password">` for client credentials: the browser password manager autofilled them ("Elfina.8990" case) — use `CampoSecreto` (text + CSS masking, autocomplete off). `/tecnicos/productos-digitales` is a compact sortable table (newest first) with a side panel (masked credentials with Show/Copy, PDF). "Producto Digital" mixes name·state·date: show `nombreLimpio()`. Point 5B-1: approving a budget NEVER picks a license (`planDeCarga` → "Por entregar: elige la licencia."); the line gets "Entregar licencia" (`components/tecnicos/ordenes/EntregarLicencia.tsx`, `GET|POST /api/tecnicos/ordenes/[id]/presupuesto/[lineaId]/licencia`), which loads the chosen unit through `cargarLicenciaEnLinea` (cargar.ts, with post-write check against two people taking the same unit) and offers "Reemplazar" with a reason (`reemplazarLicenciaEnLinea`: the old unit goes back to stock only if its PDF was never generated, otherwise "Anulado"). Linking a unit to an order sets "Reservado"; only the invoice/receipt sets "Usado"; voiding returns it to "Reservado" if it is still linked to its order. Pure rules: `lib/productos-digitales/entrega.ts`. "Entregar al cliente" also requires each license of the order to have its PDF. Point 5B-2 (owner's design, 7-nov-2026): a license enters ONLY through its purchase — `/shipping-v2/items/nuevo?tipo=digital` (`RegistrarLicenciasForm`, Staff/Admin only via `puedeGestionarLicencias`/`puedeComprar`): OC header (Software providers), one row per license (catalog product, credentials by type, duration, cost, price, "Reposición del proveedor ($0)" → "Regalo de proveedor"), payment "Ahora" defaulting to "Tarjeta D. Supe Geek " (→ SGINGRESOS). Each row → `POST /api/shipping-v2/licencias`: creates the Shipping item (category "Licencia digital", typecast, in the store, inside its OC) + the DIG unit linked by "Artículo Shipping" (if the DIG fails the item is undone with `deshacerArticuloDeLicencia`) and, with a solicitud, `aplicarCompraDeLicencia` loads it on the order line. Approving a digital line creates its purchase request (`planDeCarga` → `crear_solicitud`, category "Licencia digital", no down payment required: `coberturaAnticipo` treats it as covered and it does not consume the payment); the line shows the chip + "Comprar" (Staff/Admin) and "Usar una del inventario" (`EntregarLicencia`, which auto-cancels the request via `cancelarSolicitudPorStock`). The DIG unit drives its item (`planArticuloDeLicencia` in `lib/productos-digitales/compra.ts`, applied by `sincronizarArticulosDeLicencias` from assign/release/annul, invoice/receipt emission and voiding, with Kardex): Disponible→Disponible, Reservado→Reservado, En reclamo→Con novedad, Usado→Vendido (qty 0), Anulado→Dado de baja (or stays Vendido); "Disponible para venta" is always false and the billing search excludes category "Licencia digital" (sold only through its DIG). `/tecnicos/productos-digitales` has no "Nuevo producto" (POST returns 410): management is `GestionLicencia` + `POST /api/tecnicos/productos-digitales/[id]/gestion` (editar · reclamo "En reclamo" · resolver funcionó/repuesta/no repuesta · anular · Ver compra). Point 5C (8-nov-2026, with 14): "Producto Digital" (text) stores ONLY the catalog name (the purchase route writes it; screens read the "Nombre Producto" lookup first); the duplicate catalog "Microsoft Office 365 Education" was merged into "Microsoft 365 Education (PC, Mac)" and deleted (data fix `scripts/ajuste-auditoria-ops-punto5c.ts`, pure plan `lib/productos-digitales/ajuste-5c.ts`); creating a catalog product warns about similar existing names (`posiblesDuplicadosCatalogo`, POST returns 409 with `duplicados` unless `confirmarDuplicado`).

### Pedido especial de cliente (point 10, in progress since 10-nov-2026; 10A done 12-nov)
Design and owner decisions: project doc `claude/Diseno_Fase3_Pedidos.md`. A "pedido especial" is an `Operación Comercial` whose quote lives in lines of the SAME "Presupuesto por Orden" table (link "Pedido"; inverse "Líneas del pedido" on the operación) — NOT the old "Operación Comercial" link on a line, which means "repuesto of an old order". Pure rules in `lib/pedidos-especiales/reglas.ts`: commercial states Cotizando · Esperando al cliente · Aceptado · Entregado · Cancelado (old states map via `estadoComercial`), anticipo by tiers (`anticipoRequerido`: full up to $100, 50 % above), quote validity 72 h default / 1–7 days (`venceCotizacion`, `vigencia`, internal warning 24 h before), `errorAceptar`, `planCancelacion` (before buying: refund or saldo a favor; after: saldo a favor only, item stays in store). Lines are created with `crearLineaDePedido` / read with `listarLineasDePedido`. The ONE calculator counts an accepted line ("Aprobada") via `pendientesDeLaCuenta({ lineasPedido })` until it is bought; once bought the line is "Cargada" with its item and the item is charged at the line price × the LINE's units (`unidadesDelCliente`, both readers). A line's purchase request is `asegurarSolicitudDeLinea({ pedidoId, linea })` (operación + línea, no orden); buying it reserves the item for the operación and loads the line (`apartarParaQuienLoPidio`), and the pedido stays "Aceptado". In the purchase inbox a pedido's anticipo is measured over the whole pedido (`coberturaAnticipo(..., "pedido_especial")`). New Airtable fields on the operación: "Enlace pedido token/intentos/bloqueado hasta", "Cotización vence", "Aceptado en/por/vía". Point 10A-2 (screen): every NEW operación is created "Cotizando" (never linked to an order — separation orden/pedidos, 10A-0 closed the old links); `esPedidoEspecial` decides whether the detail shows `CotizacionPedido` (lines as "Alternativa" = group "pedido", the client picks one, or "Adicional"; "Enviar cotización"/"Renovar" with 1–7 days; WhatsApp text `mensajeCotizacion` without internal data; "Aceptar en tienda" → `aceptarPedido` approves the chosen lines, rejects the rest, creates their purchase requests, sets "Aceptado en/por/vía", then opens "Registrar abono" with the missing anticipo) or the old Opciones UI. Server: `lib/pedidos-especiales/servidor.ts`, route `GET|POST /api/operaciones/[id]/pedido`. The board groups by `estadoComercial` (Cotizando · Esperando al cliente · Aceptado · Entregado; Cancelado behind a toggle) and shows the quote validity; the daily cron (`depuracion.ts`) never auto-rejects a pedido especial, it notifies Staff/Admin 24 h before the quote expires. Cancelling (`cancelarPedido`) requires the money to be resolved first in the account (saldo a favor / devolver) and is blocked once something was bought (comes with 10C).
Point 10A-3 (12-nov-2026, client link): the pedido has ONE public page for life, `/mi-pedido/<token>` (token in "Enlace pedido token", created by the first "Enviar cotización", `asegurarEnlacePedido`; API `GET|POST /api/publico/pedido/[token]`, not in proxy.ts on purpose; no cost/supplier/URL/personal data). Pure rules `lib/pedidos-especiales/enlace-reglas.ts` (`construirVistaCliente` phases preparando · cotizacion · vencida · por_pagar · confirmado · entregado · cancelado; `huellaLineaCliente`, `errorEleccion`, `eleccionVigente`, `confirmacionPorPago`), server `lib/pedidos-especiales/enlace.ts`. Owner's rule: "Acepto la opción N" does NOT accept the pedido — it stores the client's CHOICE (a "Presupuesto Respuestas" record linked by "Pedido", Detalle version 3 `eleccion_pedido`) and shows how to pay (Banco Pichincha transfer with copy button, "Enviar comprobante por WhatsApp", PayPhone button wired but off: `lib/pagos/payphone.ts`). The pedido becomes "Aceptado" (vía Enlace) only when a payment covers the tier rule: `confirmarPedidoSiPagado` is the ONE door, called after every operación abono (`/api/operaciones/[id]/abonos`), after paying with saldo a favor, and later by PayPhone; the price chosen while the quote was valid is honored (`aceptarPedido({ vigenteAl })`). A choice stops counting if the employee changes a chosen line or adds something that "se suma". Store data (address, hours, WhatsApp, bank) live in `lib/tienda/datos.ts` only. The employee screen shows "Enlace" (copy) and "Eligió en el enlace … Falta $X · Registrar abono"; "Aceptar en tienda" starts from the client's choice. Open legacy pedidos were moved with `scripts/ajuste-auditoria-ops-punto10a3.ts` (pure plan `migrar-abiertos.ts`: Requerimiento → "Cotizando" with their Opciones as proposed alternatives; Pedido with item → "Aceptado" with a "Cargada" line; old Opciones kept as history; accounts compared before/after).

### Entregar al cliente (the only way to "Finalizado Entregado")
Auditoría ops, punto 6 (6-nov-2026). Like the RepairDesk/Lightspeed checkout: delivering the device IS closing the account. `PATCH /api/tecnicos/ordenes/[id]/estado` REJECTS "Finalizado Entregado"; the order screen's "Entregar al cliente" button opens `components/tecnicos/ordenes/EntregarClientePanel.tsx`, which calls `GET|POST /api/tecnicos/ordenes/[id]/entregar` (`lib/entrega/servidor.ts`, pure rules in `lib/entrega/reglas.ts`).
